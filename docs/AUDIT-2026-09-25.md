## 2. P0 — fix before anything else

### P0-1 · Pro membership is free for everyone in production (revenue bypass)

`server/src/routes/billing.routes.ts` exposes `POST /api/subscription/web`, and `subscription.service.ts#upgradeWeb` writes `tier: PRO, status: ACTIVE, expiresAt: now + durationDays` with **no payment provider involved**. The code comments call it a "dev path", but it is mounted unconditionally in production.

Proven locally against a running server:

```
tier BEFORE: FREE
POST /api/subscription/web {"productKey":"WEB_YEARLY"}  →  200
{"tier":"PRO","status":"ACTIVE","platform":"WEB","productId":"skillswap_pro_web_yearly",
 "expiresAt":"2027-09-2…"}
tier AFTER : PRO
```

The route is live on Render too (`POST https://skillswap-api-dcg8.onrender.com/api/subscription/web` → `401 UNAUTHORIZED`, i.e. it exists and only wants a session cookie). Any signed-in user — **including Android users who are supposed to pay through Google Play** — can get a year of Pro with one `curl` using their own cookie. `client/src/lib/billing-bridge.ts` already does exactly this on web (`purchaseToken: web-mock-${Date.now()}`).

Compounding it: `render.yaml` sets `PLAY_BILLING_VERIFY: 'false'`, and `playBillingVerifier.ts` then returns `{ valid: true }` for **any** `purchaseToken` string ≥ 5 chars. So the paid Android path is also unenforced.

**Fix**
1. Refuse the web upgrade in production unless an explicit `ENABLE_WEB_BILLING=true` is set (or replace it with a real web provider — Stripe/Paystack).
2. Set `PLAY_BILLING_VERIFY=true` in `render.yaml` and supply `GOOGLE_PLAY_SERVICE_ACCOUNT_JSON`.
3. Reject `/subscription/web` when the request comes from the native app (platform check), so Play Billing cannot be side-stepped.
4. Add a test that asserts a non-production environment refuses the free upgrade.

**Impact if unfixed:** Pro tier, boosts, "who viewed me" and all free-tier limits (3 pending requests / 5 exchanges) are unenforceable. Zero possible revenue.

### P0-2 · CORS reflects any origin *with credentials*

```ts
// server/src/index.ts
cors({ origin: env.CLIENT_URL === '*' ? true : env.CLIENT_URL, credentials: true })
```

`render.yaml` sets `CLIENT_URL: '*'` → `origin: true`, which echoes the caller's `Origin` back and allows credentials. Any website a logged-in user visits can make authenticated cross-origin requests to the API **and read the responses** (profile, matches, messages, notifications) — and, combined with P0-1, upgrade itself to Pro. Auth is cookie-based, so this is a straight CSRF/data-exfiltration vector.

**Fix:** explicit allowlist — the Render domain, `capacitor://localhost`, `https://localhost` (Android WebView), plus `http://localhost:5173` in dev. Never `true` with `credentials: true`. Consider a CSRF token or `SameSite=Strict` on the auth cookie for browser clients (native uses the bearer token, so it is unaffected).

### P0-3 · Every deploy runs `prisma db push --accept-data-loss`, and there are no migrations

```
buildCommand: … npx prisma db push --accept-data-loss --skip-generate …
```

`server/prisma/migrations/` does not exist — the schema has never been versioned. `db push --accept-data-loss` lets Prisma **drop columns and tables containing real user data** whenever the schema and the database diverge, silently, as part of a normal deploy. With live accounts, exchanges, messages and reviews on Render, this is the single most likely cause of an unrecoverable incident.

**Fix**
1. Take a baseline from the *current production* schema: `prisma migrate diff --from-empty --to-schema-datamodel prisma/schema.prisma --script > migrations/0_init/migration.sql`, then `prisma migrate resolve --applied 0_init`.
2. Change `buildCommand` to `npx prisma migrate deploy` and delete `--accept-data-loss`.
3. Add nightly `pg_dump` (Render's free Postgres has no PITR) — even a cron to a bucket is enough.

## 3. P1 — correctness and integrity

### P1-4 · Two divergent skill catalogues (production ≠ development)

| Source | Used by | Skills | Categories |
| --- | --- | --- | --- |
| `server/src/catalogue.ts` | `npm run seed` (dev) | **288** | 14 |
| `server/scripts/seed-prod.js` | **every Render deploy** | **225** | 12 |

`seed-prod.js` is a hand-copied JavaScript duplicate of the TypeScript catalogue and has drifted 63 skills / 2 categories behind. Production users see a smaller skill list than you develop against, and anything keyed on the missing skills behaves differently in prod.

**Fix:** make `seed-prod.js` import the compiled catalogue (`require('../dist/catalogue')` after `build:prod`, which already runs earlier in the same build command) and delete the duplicated array. One source of truth.

### P1-5 · The test suite cannot run as configured, and tests nothing real

Two independent defects:

1. **Memory.** `jest.config.js` uses ts-jest with full type-checking. Because `src/lib/prisma.ts` pulls in the generated Prisma client (31 models) and the dependency tree includes `googleapis` (211 MB on disk), every suite — even a 35-line pure unit test — balloons to ~930 MB and the runner dies with `FATAL ERROR: Ineffective mark-compacts near heap limit`. Setting `isolatedModules: true` (transpile-only) makes the same 5 suites pass in **0.7–2 s**.
2. **Database.** `server/tests/setup.ts` hardcodes `postgresql://localhost:5432/skillswap_test` — no user, no password. Prisma resolves that to an empty username and fails with `P1010: User `` was denied access`. It never surfaces today only because **no test actually touches the database**: `matching.test.ts` makes 0 `prisma.*` calls, and `password-reset.test.ts` mocks `../src/config/env`, `../src/lib/prisma` and `nodemailer`.

So the 58 passing tests are all unit/mocked. There is **zero integration coverage** of signup, matching, requests, exchanges, messaging, sessions, reviews, blocking, admin or entitlements — the exact surfaces where P0-1 lives.

**Fix:** `isolatedModules`/transpile-only transform, `TEST_DATABASE_URL` from the environment with a per-run schema reset, then real HTTP-level integration tests. A 117-test Vitest + Supertest integration suite already exists in the parallel build at `/home/user/skillswap-local-mvp` (auth 17, matching 19, exchange requests 18, exchanges 16, reviews 10, authorization 12, profile/skills 12, matching unit 13) and can be ported onto this schema.

### P1-6 · `npm run seed` and the Prisma CLI fail on a fresh clone

The app loads the **root** `.env` (`server/src/config/env.ts` → `path.resolve(__dirname, '../../../.env')`), but:
- the Prisma CLI is invoked from `server/`, so it looks for `server/.env` / `server/prisma/.env` and never sees the root file → `error: Environment variable not found: DATABASE_URL`;
- `prisma/seed.ts` runs under plain `tsx` with no `dotenv` import at all → `PrismaClientInitializationError … Environment variable not found: DATABASE_URL`.

The README's setup steps therefore fail for anyone cloning the repo. (I worked around it locally with a gitignored `server/.env` symlink plus an exported `DATABASE_URL`; nothing was committed.)

**Fix:** add `dotenv.config({ path: …root .env })` to the top of `seed.ts` and the other standalone scripts, and add a `server/.env.example` pointer or a `dotenv-cli` wrapper in the `prisma:*` npm scripts.

### P1-7 · Token lifetime and revocation

- `render.yaml` sets `JWT_EXPIRES_IN: 365d`.
- `POST /api/auth/signup` and `/login` return the raw JWT **in the response body** as well as the cookie.
- `POST /api/auth/logout` only clears the cookie — there is no token version, `jti` denylist, or session row.

A token captured once (logs, a proxy, a compromised page via P0-2, an old APK) stays valid for a year and survives logout, password change and deactivation. **Fix:** store a `tokenVersion` on `User`, bump it on logout/password-change/deactivate and check it in `requireAuth`; keep the body token only for the native socket handshake and shorten the web lifetime.

## 5. What is solid — do not churn these

- **Matching engine is exactly per spec and genuinely deterministic**: `+50` they teach what you want, `+30` you teach what they want, `+10` same university, `+5` compatible format, `+5` compatible availability, max 100; tiers 80/60/40; excludes self, inactive users and blocks in both directions. No AI anywhere.
- **Match queries are bounded and batch-loaded** — `take: 200` on candidates, one `findMany` for profiles, one for subscriptions. No N+1.
- **Socket.IO authorization is correct** — JWT from the handshake cookie (or `auth.token` for native), `exchange:join` verifies `userAId/userBId` membership and `ACTIVE` status before joining the room, and message/call handlers re-check membership and status.
- **Layering is clean**: `routes → services → prisma`, zod validators, `asyncHandler`, central error handler, helmet, auth-specific rate limit (20/15 min), bcrypt cost 10, idempotent additive seeding that never touches real accounts.
- **No secrets committed** — `.env` is gitignored, nothing sensitive in git history, zero `TODO`/`FIXME` debt markers.
- **Both apps type-check clean and the client builds**, and the deployed service is up and serving the SPA.

## 6. Recommended order of work

1. **P0-1 + P0-2** (same afternoon): gate the web upgrade, enforce Play verification, lock CORS to an allowlist. These are the two that cost you money and user data.
2. **P0-3 + P1-4**: baseline migration + `migrate deploy`, single skill catalogue. Protects production data and makes prod match dev.

5. **P2-9 → P2-14**: performance, TURN, public catalogue, CI, cron.
